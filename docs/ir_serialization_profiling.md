# IR Serialization/Deserialization Profiling

## Goal

Quantify the cost of converting Triton TTIR modules to text and parsing that
text back into MLIR modules. This is separate from end-to-end compile time and
Pass profiling:

```text
kernel compile (once, setup only)
  -> real .ttir files in Triton cache
  -> parse source TTIR modules (setup only)
  -> timed serialization/deserialization repeats
  -> JSON/CSV/Markdown result
  -> compare PR head against cached base SHA
```

The timing code is only executed by `ir_serialization_benchmark.py`. It does
not add timers or file operations to normal Triton compilation.

## Metrics

For every kernel, all `.ttir` files generated by its compile worker are handled
as one sample set. A repeat records:

| Metric | Timed operation |
| --- | --- |
| `serialize` | `str(module)` for every module |
| `write_text` | write all serialized strings as UTF-8 files |
| `read_text` | raw UTF-8 reads of those files |
| `deserialize` | `ir.parse_mlir_module(file, context)` for every file |
| `parse_estimate` | `max(0, deserialize - read_text)` |
| `roundtrip` | `serialize + write_text + deserialize` |

`deserialize` is the authoritative file-based deserialization metric. It
includes opening/reading the file, MLIR parsing, and cloning the parsed module,
because that is the boundary exposed by the current C++ binding.
`parse_estimate` is diagnostic only: subtracting a separately timed raw read
does not perfectly isolate parser CPU time.

The default CI comparison uses `serialize` and `deserialize`. File I/O and
round-trip measurements remain available in the result artifacts and
dashboard.

## Regression Policy

For PR tasks, the server uses the exact base SHA from `ci/base/pr-<number>`.
It looks for:

```text
ir-serialization/by-sha/<base-sha>/<backend-profile>/latest.json
```

If absent, the base commit is measured once and cached. The PR result is a
warning when a selected metric meets all of these conditions:

1. candidate median is slower than the base median;
2. slowdown is greater than `IR_SERIALIZATION_THRESHOLD` (default 20%);
3. base median is at least `IR_SERIALIZATION_MIN_BASE_MS`;
4. absolute increase is at least `IR_SERIALIZATION_MIN_DELTA_MS`.

A missing base result is also a warning. Benchmark execution or parse failure
still fails local CI. Since GitHub commit statuses have no warning state, a
performance warning is published as a successful status whose description
names the warning category.

## Artifacts and Dashboard

Each run can publish:

```text
ir-serialization.log
ir-serialization.json
ir-serialization.csv
ir-serialization-summary.md
ir-serialization-base.json
ir-serialization-comparison.json
ir-serialization-comparison.csv
ir-serialization-comparison.md
ir-serialization-comparison.log
```

Stable baselines and dashboards are written to the Gitee results branch:

```text
ir-serialization/by-sha/<sha>/<backend-profile>/latest.json
ir-serialization/by-sha/<sha>/<backend-profile>/latest.csv
ir-serialization/by-sha/<sha>/<backend-profile>/latest.md
ir-serialization/dashboard.md
ir-serialization/dashboard.csv
```

The dashboard is derived from SHA-indexed JSON files on every publication; it
is not an independent source of truth.
